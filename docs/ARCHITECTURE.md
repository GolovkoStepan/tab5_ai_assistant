# Архитектура прошивки

Документ описывает, как устроен код: слои, модули, форматы файлов на SD и
контракты инструментов агента.

Связанные документы: [`DEVELOPMENT_PLAN.md`](DEVELOPMENT_PLAN.md) (этапы),
[`DECISIONS.md`](DECISIONS.md) (почему так), [`DEPENDENCIES.md`](DEPENDENCIES.md)
(версии).

---

## 1. Принципы

1. **Логика отдельно от железа.** Всё, что можно проверить без платы, живёт в
   чистых функциях и тестируется в `env:native`. Железо — тонкий слой адаптеров.
2. **Готовые библиотеки M5Stack — прежде всего.** Дисплей, тач, батарея, RTC,
   IO-экспандеры и клавиатура берутся из M5Unified/M5GFX/M5UnitUnified, а не
   переписываются.
3. **Один поток владеет экраном.** Отрисовка только из UI-задачи; сеть и агент
   работают в отдельной задаче и передают события через очередь.
4. **Всё состояние на диске переживает перезагрузку.** Треды, документы,
   настройки — на SD/NVS, в RAM только кэш.
5. **Деградация, а не отказ.** Нет сети — читаем документы; нет SD — говорим об
   этом прямо; нет батареи — работаем от USB.

## 3. Задачи (FreeRTOS)

Отдельных задач под сеть и агент **нет** — и это осознанно. Всё живёт в одном
цикле `loop()` (задача Arduino), а долгие операции сделаны неблокирующими:

| Что | Как | Почему так |
|---|---|---|
| Стриминг ответа | `ApiClient::start()` запускает запрос и сразу возвращает управление, `tick()` забирает только уже пришедшие данные | блокирующее чтение заморозило бы экран на всё время ответа, и `Esc` не обрабатывался бы |
| Подключение к Wi-Fi | `start_connect()` + `tick()` | `WiFi.begin()` с ожиданием держал бы UI до 20 с — на экране это неотличимо от зависания |
| Скан сетей | `scanNetworks(true)` + `scanComplete()` | то же |
| Время | `clock_sync::tick()`: один запрос SNTP при появлении сети | ждать ответа NTP в `setup()` незачем |
| Батарея, часы, автосохранение | опрос по `millis()` в общем цикле | отдельная задача ради «раз в 10 с» — лишние 8 КБ стека |

Почему не отдельная сетевая задача: каждое TLS-соединение ест ~32 КБ
внутренней RAM, а обмен через очередь событий добавил бы целый слой
синхронизации ради одного запроса за раз. Неблокирующий клиент даёт тот же
отзывчивый интерфейс дешевле. Если появится второй параллельный запрос
(например, веб-поиск во время стриминга), к этому решению придётся вернуться.

## 4. Модули

### 4.1 UI

Собственный минимальный набор виджетов поверх M5GFX — без LVGL.

| Компонент | Ответственность |
|---|---|
| `Screen` | базовый интерфейс: `onEnter`, `onExit`, `onKey`, `onTick`, `draw` |
| `ScreenStack` | навигация: чат → список тредов → настройки, возврат по `Esc` |
| `StatusBar` | Wi-Fi, раскладка (РУС/ENG), заряд в %, время, токены за сессию |
| `MessageList` | лента сообщений: перенос строк, прокрутка, автоскролл к низу |
| `TextInput` | поле ввода с кареткой: `←`/`→` по символам, `Ctrl+←/→` в начало и конец, `Backspace`/`Delete`, горизонтальная прокрутка длинной строки |
| `MarkdownLite` | «как есть» в MVP: только переносы и сохранение пробелов |
| `KeyHints` | нижняя строка подсказок для текущего экрана |

Шрифт: `lgfx::fonts::efontJA_16` (Efont Biwidth) — кириллица, `«»`, `№`,
стрелки, `—`, `…`. Покрывает 171 нужный символ из 172 (пустой только пробел).
Моноширинный для кода — `efontCN_16`.

> **Не брать `lgfxJapanGothic_16`.** В нём `\` нарисован как `¥` (шрифт следует
> JIS X 0201), а `_` — пустой глиф, то есть не рисуется вообще. Для чата это
> терпимо, для редактора кода и путей — нет: `snake_case` читается как
> `snake case`. Подробности — [`HARDWARE_VERIFICATION.md`](HARDWARE_VERIFICATION.md),
> грабли 6.
>
> **Эмодзи в шрифте нет ни одного.** U+1F600, U+1F44D, U+2705, U+2764, U+263A
> проверены разбором таблицы глифов — «глифа нет». Отсутствующий символ M5GFX
> рисует рамкой (`IFont::drawCharDummy`), а не пустым местом, поэтому ответ
> модели с эмодзи превращается в `☐☐☐`. Экрану нужен растровый шрифт с
> картинками, а это другой порядок размера и отдельная задача; пока в системную
> инструкцию (`kSystemPrompt` в `ui/chat_screen.cpp`) дописано требование не
> использовать эмодзи и пиктограммы. Обычные знаки — `·`, `—`, `…`, `«»`, `№`,
> `→ ← ↑ ↓`, `•`, `★`, `●`, `■` — в шрифте есть.

Отрисовка чата: перерисовываем только изменившуюся область. Полный кадр
1280×720×2 Б = 1.84 МБ, его в PSRAM держать можно, но без нужды не нужно.

**Счётчик строк ленты — инкрементальный, и это источник тонких ошибок.**
`ChatScreen` держит кэш «сколько строк занимает каждое сообщение»: пересчитывать
тред на двести сообщений каждый кадр нельзя, а кадры идут на каждом куске
стриминга. Считать заново приходится только новые сообщения и то, которое
растёт. Вопрос «с какого сообщения» вынесен в `util/chat_measure` с тестами на
хосте — потому что ошибка здесь не косметическая: заниженный `total_lines`
делает его меньше высоты экрана, и тогда прокрутка считает, что прокручивать
нечего (стрелки не двигают ленту), а окно обрывает ответ.

Признак пересчёта — **изменение длины последнего сообщения**, а не режим экрана.
Так было не сразу: условие «идёт ответ» пропускало ответ, пришедший целиком за
один `tick()` (быстрая модель, медленная отрисовка) — к первому кадру экран уже
снова Idle. На плате ответ в 5 КБ считался за 2 строки вместо 64.

**Правило: не перерисовывать экран целиком по событию.** `fillScreen` плюс
несколько сотен примитивов дают заметное мерцание — на bring-up это проявилось
на касании тача. Для графики поверх содержимого (курсор, маркер) сохранять
область через `readRect` и возвращать `pushImage`. Для повторяющихся элементов
(ячейки, строки списка) сравнивать состояние с предыдущим и трогать только
изменившиеся. Правило и пример кода — в
[`HARDWARE_VERIFICATION.md`](HARDWARE_VERIFICATION.md), грабли 5.

**Прокрутка ленты сдвигает готовое изображение, а не перерисовывает её.**
У панели здесь **один** фреймбуфер (`dpi_config.num_fbs = 1` в
`Panel_DSI.inl`), переключения страниц нет — рисуем прямо в тот буфер, который
сейчас сканируется на экран. Поэтому любая долгая операция видна как артефакт:
сплошная заливка ленты 1280×510 занимает 33 мс, и всё это время на месте ленты
пусто. Полный кадр ленты стоил 110–170 мс при автоповторе стрелки 60 мс —
экран не успевал дорисоваться, поверх шла чёрная волна.

Отсюда три следствия, все обязательные:

1. **Сдвиг вместо перерисовки.** `ChatScreen::shift_feed()` двигает готовое
   изображение через `copyRect` и дорисовывает только открывшуюся полосу —
   57 мс вместо 170. Сдвиг применяется, лишь когда лента занимает экран
   целиком и окно не поменяло «форму» (`lines_used == max_lines`): иначе
   строки лягут в другие `y` и сдвиг разъедется с содержимым.
2. **Никакой сплошной заливки перед текстом.** Строка заливается прямо перед
   своим текстом, поэтому сплошь чёрной не бывает. Фон под каждым глифом
   (`ui::text` с `bg`) стоит почти столько же, сколько глиф, — на ленте это
   222 мс против 125, поэтому там используется `ui::text_plain`.
3. **Оверлеи — вне области сдвига.** Надписи «↑ выше»/«↓ ниже» рисовались
   пикселями внутри ленты и на время `copyRect` оказывались в двух местах
   сразу. Их заменила полоса прокрутки в правом поле (`draw_scrollbar`), а
   ширина копирования ограничена `feed_w - kMarginX`, чтобы её не задевать.

И отдельно: **прокрутка на границе не должна просить перерисовку**. Когда
стрелка зажата, а лента уже отмотана до конца, содержимое не меняется, но
прежний код всё равно ставил `_redraw_feed` — получался полный кадр 130 мс на
каждое нажатие. Теперь кадр просится только при реальном изменении `_scroll`.


### 4.2 Клавиатура

Обёртка над `m5::unit::UnitTab5Keyboard` (официальная библиотека M5Stack).

**Режим Normal** (`0x10 = 0`): событие — один байт, в котором закодирована
физическая позиция клавиши. Это нужно, чтобы маппить и латиницу, и кириллицу
своими таблицами.

```
Транзакция: read(0x02) → сколько событий в очереди (0..32)
            read(0x20) → pop одного события
Байт: [7] = нажатие (1) / отпускание (0)
      [6:4] = строка матрицы (0..4)
      [3:0] = столбец матрицы (0..13)
Пусто = 0xFF
```

Матрица 5×14, 70 клавиш. Спецклавиши по позициям: `(0,0)` esc, `(2,13)` backspace,
`(3,13)` enter, `(3,11)` ↑, `(4,10)` ←, `(4,11)` ↓, `(4,12)` →, `(4,13)` space,
`(3,0)` sym, `(3,1)` Aa, `(4,0)` ctrl, `(4,1)` alt.

Character-режим (`0x10 = 2`) отдаёт готовую латинскую строку и модификаторы — он
проще, но для кириллицы всё равно требует перемаппинга без знания физической
клавиши. Оставлен как резерв.

**Русская раскладка.** Клавиатура отдаёт позиции клавиш, поэтому ЙЦУКЕН
маппится в нашей прошивке:

```cpp
// Упрощённо: латинская буква → русская по раскладке ЙЦУКЕН
static const char* kRuMap[] = {"й","ц","у","к","е","н","г","ш","щ","з","х","ъ",
                               "ф","ы","в","а","п","р","о","л","д","ж","э",
                               "я","ч","с","м","и","т","ь","б","ю"};
```

Переключение — `Ctrl+Space` или тап по индикатору в статус-баре. Состояние
хранится в NVS. `Aa` (Caps Lock) работает в обеих раскладках.

### 4.3 Сеть

`ApiClient` — тонкая обёртка над `HTTPClient` + `NetworkClientSecure`.

```
POST https://routerai.ru/api/v1/chat/completions
Authorization: Bearer <ключ>
Content-Type: application/json
Accept: text/event-stream

{"model":"...","messages":[...],"stream":true,"tools":[...],"temperature":0.3}
```

Особенности реализации:

- **Один запрос за раз.** Второй ждёт освобождения — так меньше пик по RAM.
- **Стриминг обязателен.** Ответ ждать целиком на 1280×720 невыносимо.
- **Тело запроса и буферы — в PSRAM** (`heap_caps_malloc(..., MALLOC_CAP_SPIRAM)`
  с фолбэком на `malloc`), а не в куче по умолчанию: история легко даёт
  десятки килобайт, и рядом с TLS внутренней RAM не хватит.
- **Таймауты:** подключение 30 с, тишина в потоке 60 с, весь запрос 5 мин.
  `HTTPClient::setTimeout()` принимает **миллисекунды** — перевод в секунды
  давал таймаут 60 мс и рвал каждый запрос (найдено на плате).
- **Без gzip.** Нужен miniz, а внутренняя RAM дороже трафика. Для стриминга
  сжатие ещё и мешает читать ответ по мере прихода.
- **Повтор при 429/5xx — отдельное состояние `State::RetryWait`.** `tick()`
  только проверяет время и не блокируется, поэтому во время паузы экран жив и
  `Esc` отменяет запрос. Пауза берётся из `Retry-After` (не дольше 30 с; дату в
  этом заголовке не разбираем — неверная дата дала бы паузу в годы), иначе
  экспоненциально 2 и 4 с. Тело ошибки сохраняется ДО повтора: после
  исчерпания попыток показывается причина от сервера, а не «сервер занят».

#### 4.3.1 Подключение Wi-Fi (`hw/wifi`)

P4 своего радио не имеет: Wi-Fi живёт на C6 и поднимается по SDIO через
`esp_hosted`. Два следствия, видных в коде:

- **Всё неблокирующее.** `WiFi.begin()` с ожиданием держал бы UI до 20 секунд —
  на экране это неотличимо от зависания. Поэтому `start_connect()` запускает
  подключение и сразу возвращает управление, а `tick()` снимает состояние,
  обновляет адрес и ловит таймаут.
- **`tick()` вызывается всегда**, на любом экране. Иначе подключение, начатое
  автозапуском в `setup()`, никогда не завершится: некому будет заметить
  `WL_CONNECTED`.

Скан — асинхронный (`scanNetworks(true)`), результат забирается по
`scanComplete()`. Список сетей готовит `util/wifi_list` (чистые функции с
тестами на хосте): схлопывает дубликаты одного SSID по сильнейшему сигналу —
квартира с репитером иначе занимала пол-списка одинаковыми строками —
отбрасывает скрытые сети, сортирует устойчиво (при равном уровне порядок
сохраняется, иначе пункты менялись бы местами между сканами).

**MAC читается не сразу.** Сразу после `WiFi.mode()` драйвер отдаёт
`00:00:00:00:00:00`: `esp_hosted` поднимается в фоне. Адрес подхватывается в
`tick()`, когда станет настоящим. На живой плате это проявилось, как только
убрали `delay` со сканированием, который раньше маскировал гонку.

#### 4.3.2 Экран Wi-Fi (`ui/wifi_screen`)

`Ctrl+W` открывает экран, `Esc` возвращает (из пароля — в список, из списка —
на диагностику). Режимы: скан → список → пароль → подключение. Выбор стрелками
или касанием, `Del` — повторный скан (сеть могли включить позже).

Правило то же, что для всего UI: **полный кадр только при смене режима**.
Нажатие в поле пароля трогает только поле, таймер подключения — только полосу
прогресса, и то лишь при изменении заливки. Иначе ввод мерцал бы на каждой
букве.

**Пароль сохраняется в NVS только после успешного подключения.** При опечатке
в NVS остался бы неверный пароль, и следующая загрузка давала бы «не удалось»
без объяснения. При автоподключении к сохранённой сети пароль из буфера не
пишется вовсе — буфер пуст, и запись затёрла бы рабочий пароль пустой строкой.

#### 4.3.3 Часы (`hw/clock`)

Три источника времени, и путать их нельзя:

| Источник | Когда верен | Что с ним делать |
|---|---|---|
| RTC (RX8130) | пока заряжен суперконденсатор | прочитать при старте, записать после NTP |
| Системные часы ESP-IDF | после `settimeofday` | рабочий источник для `time()` |
| NTP | только при живом Wi-Fi | один запрос, когда сеть поднялась |

`M5.begin()` сам вызывает `Rtc.setSystemTimeFromRtc()`, поэтому при заряженном
RTC системные часы осмысленны сразу. На новой плате суперконденсатор пуст, RTC
отдаёт `2000-01--1`, и системные часы остаются на нуле — тогда единственный
источник NTP.

Таймзона из `config.json` (`timezone`, формат POSIX — `MSK-3`) выставляется
переменной `TZ` в `clock_sync::begin()`. Это нужно до создания первого треда:
метки в JSONL пишутся местным временем со смещением
(`2026-11-24T10:47:57+03:00`), а `localtime_r()` без `TZ` считал бы UTC.

`clock_sync::tick()` вызывается каждый кадр. Признак сверки — штатный
`sntp_get_sync_status() == SNTP_SYNC_STATUS_COMPLETED`; читать его можно один
раз, при чтении lwIP сбрасывает статус. После сверки время пишется в RTC
в **UTC** (драйвер при чтении пересчитывает его через `mktime` с `GMT0`) —
иначе после перезагрузки часы уехали бы на величину смещения.

Время меньше 2020-01-01 считается невыставленным (`kMinValidEpoch`): до
синхронизации `time()` возвращает секунды с загрузки, и именно из-за этого
треды когда-то назывались `chat-19700101-005946`.

### 4.4 Агент

```
пользователь → [модель] → есть tool_calls? ──нет──→ ответ в чат
                   ↑                │
                   │               да
                   │                ↓
                   └──── результат инструмента (≤4 КБ)
```

Лимит — **8 шагов**. Каждый вызов инструмента виден в чате одной строкой:
`🔍 поиск: «сброс ошибки очистителя»`. Ошибка инструмента возвращается модели
текстом, а не модалкой. `Esc` прерывает и стриминг, и цикл.

`ToolRegistry` хранит: имя, JSON-схему, валидатор аргументов, обработчик.

### 4.5 Хранилища

| Хранилище | Что | Где |
|---|---|---|
| `SettingsStore` | Wi-Fi, API-ключ, модель, пороги, раскладка, таймзона | NVS (секреты) + `/sdcard/config.json` (остальное) |
| `ChatStore` | Треды и сообщения | `/sdcard/chats/<slug>.jsonl` |
| `DocStore` | Документы с фронтматтером | `/sdcard/notes/<тема>/<slug>.md` |

Разделение: **секреты только в NVS**, потому что SD-карту легко вынуть и
прочитать на компьютере. Несекретные настройки — в `config.json`, чтобы их можно
было править руками и бэкапить.

**Грабли: `SD_MMC.open()` берёт путь от точки монтирования.** `SD_MMC.begin("/sdcard")`
монтирует ФС в эту точку, поэтому внутри уже неё путь пишется без префикса:
`SD_MMC.open("/config.json")` — это `/sdcard/config.json` на карте. Полный путь
`"/sdcard/config.json"` превращается в `/sdcard/sdcard/config.json`, `fopen`
возвращает `ENOENT`, и конфиг молча не создаётся — на экране всё выглядит
нормально. Поэтому в `app_config.h` пути хранятся **относительно** корня SD,
а инвариант закреплён тестом `test_sd_paths_are_relative_to_mount_point`.

**Первый запуск создаёт файл.** Если `config.json` отсутствует или не разобрался,
`SettingsStore::begin()` записывает эталонный файл со значениями по умолчанию —
иначе нечего править руками и нечего бэкапить. Ошибка записи не фатальна: без
SD-карты работаем на значениях по умолчанию.

**Список тредов читает только начало файлов.** `ChatStore::list_threads()`
возвращает ровно `cap` самых свежих тредов: обход каталога идёт в произвольном
порядке, поэтому массив всё время держится отсортированным по убыванию имени, а
всё, что старше последнего элемента, отбрасывается. Заголовок берётся из начала
файла (до четырёх строк) в одном буфере PSRAM на весь список: 16 КБ на стеке
задачи цикла не помещаются, а `kMaxLineBytes` — это максимальный размер строки
треда. Полное чтение треда на каждый вход в список означало бы мегабайты с SD.

**Открытие и удаление тредов — не работа экрана списка.** `ThreadsScreen` только
выставляет запрос (`take_selected_slug`, `take_new_request`,
`take_open_removed`), а выполняет его `main`: открытие треда означает ещё и
переход в чат, а удаление открытого требует сбросить ленту, поле ввода и
измерения. Иначе два экрана ссылались бы друг на друга.

**Прокрутка списка — сдвигом изображения, как и ленты чата.** У панели один
фреймбуфер, поэтому полная перерисовка пятнадцати строк (заливка области плюс
полсотни надписей с фоном) при автоповторе стрелки 80 мс видна как мерцание.
Окно сдвигается на строку через `copyRect`, дорисовывается одна открывшаяся
строка; смена выбора внутри неподвижного окна перерисовывает две строки.

Два следствия, на которых легко ошибиться:

- **стирать надо ту строку, которая нарисована подсвеченной** (`_drawn_selected`),
  а не тот номер, что был выбран до нажатия: между кадрами может пройти
  несколько нажатий, и это разные строки;
- **столбец полосы прокрутки не заливается никогда.** Заливка строки на всю
  ширину экрана стирала полосу на перерисованных строках, а `draw_scrollbar()`
  после точечной перерисовки не вызывается — в полосе появлялись дыры, и они
  прыгали вместе с курсором. Поэтому `scrollbar_x()` — граница и для заливки
  строки, и для ширины копирования `copyRect`.

## 5. Форматы файлов

### 5.1 Документ (`/sdcard/notes/<тема>/<slug>.md`)

```markdown
---
title: Сброс ошибки очистителя воздуха
tags: [бытовая-техника, очиститель]
source_url: https://example.com/purifier-error-reset
created: 2026-11-23T20:31:00+03:00
updated: 2026-11-23T20:31:00+03:00
---

# Сброс ошибки после замены фильтра

1. Выключить прибор кнопкой питания.
2. Зажать кнопку «Filter» на 5 секунд до звукового сигнала.
3. ...

## Источник

<https://example.com/purifier-error-reset>
```

Правила:

- **Имя файла — ASCII-слаг латиницей.** Кириллица в именах на FAT32 — источник
  проблем с VFS и сравнением имён; заголовок хранится в `title`.
- **Фронтматтер обязателен.** Без него документ не считается документом.
- **Атомарная запись:** пишем в `<slug>.md.tmp`, затем `rename`.
- **Валидация пути:** только внутри `/sdcard/notes`, запрет `..` и абсолютных путей.

### 5.2 Тред (`/sdcard/chats/<slug>.jsonl`)

Одна строка — одно сообщение. Формат JSONL выбран за устойчивость: при обрыве
записи теряется максимум последняя строка, файл остаётся читаемым.

```json
{"role":"user","content":"как сбросить ошибку очистителя?","ts":"2026-11-23T20:31:00+03:00"}
{"role":"assistant","content":"...","ts":"...","usage":{"input":1200,"output":180}}
{"role":"assistant","content":"ответ оборван","ts":"...","usage":{"input":1200,"output":180},"partial":true}
{"role":"tool","tool_call_id":"call_1","name":"web_search","content":"...","ts":"..."}
```

Имена полей `usage` — `input`/`output`, а не `prompt`/`completion`: так
называются счётчики в файле, чтобы его нельзя было спутать с ответом API, где
RouterAI присылает `prompt_tokens`/`completion_tokens`. Разбор понимает оба
варианта, но пишем всегда свой.

`partial:true` — ответ оборван (Esc, обрыв сети, лимит токенов). Без пометки
оборванный ответ неотличим от законченного, и непонятно, почему модель
замолчала на полуслове.

Служебная строка `{"type":"meta",...}` зарезервирована под заголовок и дату
создания треда: разбор её пропускает, но v0.2.0 её ещё не пишет — заголовком
служит первое сообщение пользователя. Поэтому и переименования тредов нет:
заголовок в списке — это первый вопрос, а правка его задним числом исказила бы
историю, которую видит модель.

**Список тредов** (`ui/threads_screen`, `Ctrl+T`) показывает дату из имени файла
и заголовок из первого вопроса. Читается только начало файла (до четырёх строк):
тронутый разговор на 256 КБ при входе в список не читается. Имя треда —
единственный источник даты, поэтому тред, созданный при несверенных часах, имеет
имя `chat-00000000-…` и в списке показывается с прочерком вместо даты, а не с
«00.00 00:00». Если разделитель разобрать не удалось, вместо заголовка
показывается имя файла.

**Почему файл читается целиком.** При загрузке треда файл читается в буфер,
текст всех сообщений копируется в одну арену в PSRAM, указатели сообщений
смотрят в неё. Строки файла перезаписываются по мере разбора, поэтому
указатель внутрь строки стал бы висячим. Размер файла ограничен 256 КБ:
тред больше этого не читается — обрезка истории при отправке всё равно
отбросила бы начало.

**Запись.** Вопрос пользователя дописывается в конец файла сразу (`append`), до
ответа модели: при обрыве питания теряется максимум последняя строка. Ответ
модели копится в памяти и дописывается одной строкой, когда дописан
(`flush_last`).

Перезаписи файла нет: `flush_last` именно дописывает строку, а не собирает файл
заново. Раньше он переписывал тред целиком из памяти через `.tmp` + rename, и
это оказалось опасным — любая ошибка с указателями на текст сообщений уезжала
на карту, и тред на диске исчезал. Дозапись трогает только новую реплику.
Писать на каждый токен всё равно нельзя: SD этого не любит, а при обрыве
питания посреди дозаписи теряется одна строка, а не весь разговор.

**Один буфер на все растущие ответы.** Текст ответа живёт в единственном
буфере `_tail`; арена `_arena` — для того, что больше не меняется. Поэтому
`begin_answer()` обязан переселить прошлый ответ из `_tail` в арену, иначе все
реплики модели начнут показывать текст последнего ответа. Искать его нужно по
указателю среди ВСЕХ сообщений, а не только в последнем: между двумя ответами в
тред попадает вопрос пользователя.

**Очистка треда.** `ChatStore::clear()` усекает файл до нуля (`SD_MMC.open` в
режиме `FILE_WRITE` на существующем файле) и сбрасывает память, **сохраняя имя
треда**: сброс — это очистка разговора, а не создание нового треда (`Ctrl+N`).
Именно усечение, а не `remove` с последующим созданием: если второе не удастся,
на карте не останется ни старого треда, ни нового. Память сбрасывается только
после успешного усечения — иначе экран показал бы пустой тред, а на карте
остался бы старый, и разговор «вернулся» бы после перезагрузки. На экране
`Ctrl+R` требует подтверждения вторым нажатием (`_clear_armed`), потому что
операция необратима.

## 6. Контракты инструментов агента

Все пути — относительно `/sdcard/notes`. Слаги ASCII. Результат — текст, не JSON
(модели проще читать, а мы экономим токены).

| Инструмент | Аргументы | Возвращает |
|---|---|---|
| `list_docs` | `folder?` | список: `path — title (updated)` |
| `read_doc` | `path` | полный текст файла |
| `search_docs` | `query`, `limit? = 5` | `path: сниппет с совпадением` |
| `write_doc` | `path`, `title`, `content`, `source_url?`, `tags?` | «создан» / «обновлён» + путь |
| `delete_doc` | `path` | «удалён» (после подтверждения на экране) |
| `web_search` | `query`, `max_results? = 3` | источники: заголовок, URL, выжимка |

Чего сознательно **нет**: создания папок (создаются автоматически), переименования,
перемещения, доступа к чатам. Меньше инструментов — меньше способов всё сломать.

## 7. Ошибки и восстановление

| Ситуация | Поведение |
|---|---|
| Нет Wi-Fi | Баннер в чате; документы и история доступны |
| 401 | «Неверный API-ключ» + кнопка в настройки |
| 429 | Ждём `Retry-After` (максимум 30 с), до двух повторов |
| 5xx | До двух повторов (2 с, затем 4 с), затем сообщение с числом попыток |
| Обрыв стриминга | Частичный ответ сохраняется с пометкой «ответ неполный» |
| SD не смонтирована | Работаем, но предупреждаем: документы недоступны |
| Батарея < 5 % | Сохраняем всё, выключаемся через PMS150G |
| Инструмент вернул ошибку | Текст ошибки уходит модели, она решает, что делать |

## 8. Что проверено, а что предполагается

Проверено на живой плате (подробности в [`HARDWARE_VERIFICATION.md`](HARDWARE_VERIFICATION.md)):
ревизия чипа, MAC, размер flash, заводские разделы, дамп прошивки; дисплей,
клавиатура с ЙЦУКЕН, тач, SD в 4-bit с записью, Wi-Fi через C6 (скан 16–26
сетей, подключение по паролю, автоподключение после перезагрузки); чат со
стримингом от RouterAI, запись и перечитывание тредов на SD, синхронизация
времени по NTP, прокрутка длинного ответа и списка тредов.

Предполагается и будет проверено на этапах:

- совместимость плагина `web` RouterAI с tool calling — v0.4.0;
- поведение стриминга при обрыве — v0.2.0 (на живом обрыве не воспроизведено);
- повтор при 429/5xx — написан, но живой ответ 429/5xx по запросу не получить.
